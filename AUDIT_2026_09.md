# PRIMA Runtime Audit — September 2026

Target: **single-study MRI inference on an NVIDIA RTX 4060 8 GB**, with Windows
as the host OS and WSL2/Ubuntu as the intended CUDA runtime environment.

This audit distinguishes technologies that are current from technologies that
are actually appropriate for this model and hardware.

## Executive result

The upstream research pipeline should not be used unchanged for the 8 GB target.
The `modern-runtime` branch now removes the largest avoidable GPU/RAM costs
without changing the published weights or intentionally changing the MRI input
distribution.

The remaining merge gate is hardware validation with the official checkpoint
and representative real DICOM studies.

## Adopted current stack

### PyTorch 2.14

PyTorch 2.14 was released in September 2026 and is the runtime baseline for this
branch.

Adopted capabilities:

- native variable-length attention when supported;
- PyTorch SDPA fallback;
- modern `torch.inference_mode()` / AMP path;
- optional `torch.compile`;
- `torch.load(..., mmap=True)` where checkpoint format permits it.

`torch.compile` remains OFF in the default 8 GB profiles. For a one-case
workflow, compile cold start and dynamic MRI sequence lengths can outweigh the
steady-state gain. It should be enabled only after eager-mode hardware
benchmarking.

### MONAI 1.6

The archived `monai-generative` runtime dependency is replaced by MONAI 1.6
core VQVAE. A config adapter preserves Prima's published `num_channels` schema
against MONAI core's `channels` constructor name.

### Attention backend

Runtime order in `attention_backend: auto`:

1. PyTorch native variable-length attention when the installed build/device
   supports it;
2. external FlashAttention when installed;
3. PyTorch scaled-dot-product attention fallback.

CUDA OOM is never treated as a backend-compatibility failure.

### CPU task-head quantization

The production-oriented optimized profile uses:

```yaml
quantize_cpu_heads: true
head_quant_backend: "torch_dynamic"
```

TorchAO 0.18.0 is retained as an **experimental A/B backend**, not the default.
Current 2026 CPU reports show workload-dependent performance and cases where
TorchAO dynamic INT8 is slower than PyTorch's established dynamic INT8 path.

## RTX 4060-specific memory changes

### VQ-VAE encoder only

Prima inference only calls `VQVAE.encode()`. MONAI 1.6 implements this as the
encoder forward pass, so the runtime now:

1. loads the official VQ-VAE state dict on CPU;
2. keeps only `vqvae.encoder`;
3. moves only that encoder to CUDA FP16;
4. never places the decoder or codebook on GPU;
5. deletes the encoder before loading the Prima visual backbone.

The encoder-only path is regression-tested against `VQVAE.encode()`.

### Pre-VQ Otsu filtering

The historical pipeline encoded every 3D patch with VQ-VAE and only then
applied the Otsu coordinate filter. The selected indices are determined entirely
from preprocessing metadata, not from embedding values.

The optimized profile resolves the exact same indices first and encodes only
those selected patches. The baseline profile deliberately keeps the historical
post-VQ order so the two paths can be compared on real cases. A regression test
verifies encode-all-then-filter equals filter-then-encode for an independent
per-patch encoder.

### Automatic tokenizer chunk backoff

The 8 GB profiles start with a conservative chunk size. If and only if VQ-VAE
tokenization raises CUDA OOM, the runtime halves the chunk and retries the same
tokens down to a configured minimum.

This mechanism is intentionally not used for Prima visual OOM: backbone OOM must
remain visible because it represents the actual study/model capacity limit.

### Ragged series inputs

The previous pipeline padded every MRI series to the longest series in the
study, copied those padded inputs to CUDA, and then HierViT created another
padded tensor.

The modern pipeline keeps series ragged until HierViT, removing one entire
duplicate padded representation from GPU memory.

### FP16-correct temporary tensors

Historical `torch.zeros(...).to(device)` allocations inside ViT/HierViT could
create float32 temporaries even after the visual model was converted to FP16.

Temporary buffers now inherit dtype/device from model tensors using
`new_zeros()` or vectorized indexing.

### Ragged pack/unpack vectorization

ViT and series-name transformer packing no longer performs token-by-token
Python tensor copies. Boolean indexing and vectorized gather preserve the
historical sequence order.

### Positional encoding on demand

The historical runtime precomputed a fixed 100 x 100 x 100 x 30 positional
encoding grid (roughly 120 MB in float32) even though a study uses a small
subset of those coordinates.

The runtime now computes the same sinusoidal encoding only at requested
coordinates. An equivalence test compares it against the original positional
encoding package.

### Inference-only checkpoint pruning

Historical full checkpoints retain the complete CLIP object. Full MRI inference
uses `clipvisualmodel`, not the CLIP text encoder/training criterion.

When the checkpoint alias relationship is verified, the runtime drops the
unused full CLIP/text-side object while keeping the exact same visual module
reference.

### Shared head execution cache

If multiple labels reference the same historical head module, that head is
evaluated once per study and its output is reused. Quantization also occurs once
per shared module object.

## Preprocessing / DICOM corrections

- DICOM series are streamed one at a time.
- GDCM geometry-derived ordering is preserved; files are not re-sorted by
  filename after GDCM.
- MRI arrays use float32 instead of an unnecessary float64 copy.
- 3D patch extraction is vectorized.
- Otsu/hole-fill metadata is calculated on the patch occupancy grid.
- The exactly-256-slice SimpleITK z/y/x edge case is fixed.
- Optional series-name and study-description encoders now respect their flags
  and outer sequence lengths consistently.

## Checkpoint loading

### Mmap + meta-device VQ loading

VQ-VAE state dict loading uses `weights_only=True`, attempts `mmap=True`,
constructs the model on the meta device, and uses `load_state_dict(assign=True)`
when available. This avoids allocating and initializing a duplicate random CPU
model before adopting checkpoint tensors. The path has a normal CPU fallback
and a checkpoint round-trip regression test.


The official full Prima checkpoint is still a trusted pickle full-object
checkpoint, so the compatibility loader must use `weights_only=False`.
It attempts `mmap=True` and falls back when the checkpoint serialization format
does not support memory mapping.

A safetensors-only Prima bundle is deliberately deferred until the real official
full checkpoint is audited and the exact object/state structure can be
reconstructed without guessing.

## Technologies deliberately not enabled by default

### FlashAttention 4

Not the default target for RTX 4060 Ada. Current FA4 work is primarily focused
on Hopper/Blackwell-class kernels. Native PyTorch varlen/SDPA and optional FA2
are the appropriate Ada path.

### NestedTensor / jagged rewrite

PyTorch jagged NestedTensor is promising but remains a prototype API. Prima now
gets most of the practical benefit through explicit ragged packing without
putting medical inference on a prototype representation.

### INT4 CPU heads

Not enabled. Current x86 low-bit paths still have packing/kernel caveats and
would require a larger validation burden for a medical model. INT8 is the first
quantized validation target.

### FP8 / FP4 visual model

Not enabled. RTX 4060 is Ada-class and some FP8 paths are technically possible,
but the visual backbone is accuracy-sensitive and the first objective is to
prove the FP16 model fits. FP8 is an experimental follow-up only if FP16 still
cannot fit.

### ONNX Runtime / TensorRT

Not used for the hierarchical visual transformer in this revision. Dynamic
ragged control flow makes export validation more complex.

The VQ-VAE encoder is a reasonable future ONNX/TensorRT candidate if GPU
profiling shows tokenizer latency is material after the encoder-only change.

### torch.compile by default

Disabled in the 8 GB profiles. Benchmark eager mode first. If compile is tested,
start with:

```yaml
compile_visual: true
compile_mode: "max-autotune-no-cudagraphs"
```

and retain it only if both latency and peak VRAM improve on representative MRI
studies.

## CUDA allocator

PyTorch 2.14 uses `PYTORCH_ALLOC_CONF` as the preferred allocator environment
variable; `PYTORCH_CUDA_ALLOC_CONF` remains a compatibility alias.

For dynamic MRI sequence sizes, `expandable_segments:True` is worth an A/B test
under WSL2 because it can reduce fragmentation. It is not hard-coded into the
runtime because it remains an experimental allocator option.

## Validation already in CI

The branch compiles all runtime Python sources and tests:

- vectorized volume patch extraction equivalence;
- SDPA variable-length attention math;
- Otsu patch-grid hole-fill equivalence;
- MONAI 1.6 VQ-VAE compatibility using Prima's published config schema;
- encoder-only VQ-VAE equivalence;
- on-demand positional encoding equivalence;
- PyTorch dynamic CPU INT8 smoke compatibility;
- TorchAO 0.18.0 + PyTorch 2.14 CPU INT8 smoke compatibility in a separate job;
- pre-VQ Otsu selection equivalence.

## Hardware validation required before merge

On the actual ASUS RTX 4060 8 GB:

1. audit the official full checkpoint;
2. run one representative study with the baseline profile;
3. record tokenizer peak VRAM;
4. record visual-backbone peak VRAM;
5. record CPU RAM and stage latency;
6. run the optimized CPU-INT8 profile;
7. compare every diagnosis/referral/priority output;
8. review all zero-threshold sign flips;
9. repeat on several representative studies, including a large/many-series case;
10. only then merge PR #2 into `main`.

## Final release-candidate audit additions

A final audit before hardware deployment added the following safeguards:

- raw >5000-patch series are rejected before optional pre-VQ Otsu filtering,
  preserving upstream series inclusion semantics;
- tokenizer checkpoint paths are resolved robustly from working directory,
  config directory, or repo root;
- full checkpoint compatibility recognizes historical FullMRIModel pickle paths
  including `complete_visual_model` and `full_model`, with CI round-trip tests;
- runtime config validates CUDA availability, GPU index, dtypes, and tokenizer
  chunk bounds before model work starts;
- FP32 configuration no longer enters an inappropriate CUDA autocast context;
- HierViT length tensors remain on-device via `torch.stack` instead of implicit
  scalar conversion;
- preprocessing metadata keeps the original 4-slice patch geometry immutable
  while the VQ input copy is resized to 8 slices;
- the actual attention backend used in eager inference is logged;
- preflight accepts CUDA wheel version suffixes (for example
  `2.14.0+cu130`) and warns when a CUDA 13 runtime is paired with an NVIDIA
  driver older than major version 580;
- the official weight downloader supports `--force-download` and records a
  SHA256/size manifest to avoid silently reusing an old priority checkpoint;
- local deployment configs, virtualenvs and outputs are git-ignored.

Upstream `MLNeurosurg/Prima` was rechecked during this audit. Its latest
public commit remains `604f1fc4dd7059c278d4d34bbbcaab3e404fbcd4` from
2026-07-15, which is still the base of this fork's runtime work.

Source-level comparison also confirmed that MONAI Generative 0.2.3 and MONAI
1.6 retain the VQ-VAE state-module hierarchy
(`encoder.blocks`, `decoder.blocks`, `quantizer`) and that `encode()`
remains an encoder forward pass. The constructor rename from `num_channels`
to `channels` is handled by the runtime adapter. Official checkpoint loading
on the target machine remains the final proof because the real model files are
not part of CI.
